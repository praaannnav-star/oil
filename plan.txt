3. FRAMEWORK DECISION — NO LANGCHAIN, NO LANGMAP (nothing like them is used)
------------------------------------------------------------------------------------------------
Q: Are we using LangChain (or LangMap)?
A: No. Zero LLM frameworks. Every model call is a direct Cloudflare Workers AI binding
   invocation: `env.AI.run(model, {...})`. Rationale:

   - Runtime fit ....... Workers are V8 isolates with strict CPU/ms + bundle limits;
                         LangChain.js is Node-oriented and drags heavy transitive deps.
                         Our whole backend policy is zero-dependency (P0 ethos).
   - Actual need ....... We need exactly: pinned system prompt → JSON out → validate →
                         retry once → rules fallback. That is ~40 lines (runLlmJson in
                         worker/src/routes/llm.js). A chain library abstracts problems
                         (memory, agents, vector stores) we do not have.
   - Control ........... Provenance triples {value, source, confidence} (plan §8), enum-
                         constrained outputs, nulls-over-fabrication, and audit of every
                         field are contract requirements — clearer hand-rolled than fought
                         through an abstraction.
   - Portability ....... If we later swap models/providers, only runLlmJson changes.

   What replaces LangChain's "chain": the deterministic pipeline
     prompt (prompts.js, version-pinned) → env.AI.run → fence-strip + JSON.parse
     → schema check → retry-once → rules-engine fallback → provenance annotation
   This is deliberately boring, inspectable, and demo-safe (risk R1 mitigation).

4. HOW WORKERS AI IS IMPLEMENTED (current code)
------------------------------------------------------------------------------------------------
Binding setup (worker/wrangler.toml):
     [ai]
     binding = "AI"
Deploy platform injects env.AI; no API keys, no HTTP client, per-request billing.

Models chosen:
     TEXT ... @cf/meta/llama-3.1-8b-instruct   (temperature: 0, max_tokens capped)
     ASR .... @cf/openai/whisper               (arrayBuffer audio, en-IN vocabulary hint)

Core call helper (worker/src/routes/llm.js → runLlmJson):
     1. messages = [{role:'system', content:<pinned prompt>}, {role:'user', content:payload}]
     2. res = await env.AI.run(LLM_MODEL, {messages, temperature:0, max_tokens})
     3. strip markdown fences → JSON.parse
     4. on parse/run failure → retry ONCE
     5. still failing → return null → caller falls back to deterministic rules engine
        (worker/src/lib/rules.js — ported from the client's reports.js logic)

Live endpoints (all behind Bearer JWT):
     POST /api/extract      {transcript}            → {event, provenance, source}
            event fields: discipline/activity/assetTag/qty/unit/start/end/status/blocker/date
            provenance[field] = {value, source:'llm'|'rules', confidence}; capturedAt is always
            truthful server time. Nulls allowed — NEVER invented values.
     POST /api/classify     {transcript}            → {projectId?, activityId?, discipline?,
            confidence, source} — rules-first keyword/tag scoring over live D1 activities;
            LLM tie-breaker only below 60% score, constrained to candidate ids.
     POST /api/delay-cause  {text}                  → {code∈ENUM, label, source} — rules hit
            returns immediately; LLM resolves only OTHER/NONE cases.
     POST /api/summarize    {projectId?}            → {digest:{headline,bullets,tone},
            signals[], source} — facts assembled from D1 first; model only phrases them.
     POST /api/transcribe   (audio/* body ≤5MB)     → {text} — Whisper ASR; activates the
            already-coded fallback path in js/services/speech.js when native STT is absent.

Persistence: provenance rows land in `extractions` table keyed by report_id; LLM output
ALWAYS enters via the review queue — nothing auto-applies to the schedule (state.txt §14).
